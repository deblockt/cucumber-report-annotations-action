# Developer guide

## Requirements

- Node.js 24 (the version used by the action runtime and by the CI)
- npm

```bash
npm ci
```

## Project layout

| Path | Content |
|------|---------|
| `src/index.ts` | Action entry point: calls `run` with the real `@actions/*` modules |
| `src/types.ts` | Types shared by the modules, including the subsets of `@actions/*` and `fs` used by the action |
| `src/main.ts` | `run`: reads the inputs, finds the reports, creates the GitHub check, annotations and outputs. Its dependencies (`core`, `github`, `glob`, `fs`) are injected so it can be tested with fakes |
| `src/summary.ts` | Pure functions: scenario/step counts and summary text |
| `src/check.ts` | Pure functions: check title, check status, check creation request and job failure threshold |
| `src/annotations.ts` | Builds the step annotations and the global summary annotations. The path resolution is injected |
| `src/outputs.ts` | Names and publishes the action outputs |
| `src/fileMatcher.ts` | Finds the feature file of a report in the repository |
| `src/reportReader-json.ts` | Reader for the (deprecated) Cucumber JSON report format |
| `src/reportReader-ndjson.ts` | Reader for the Cucumber message (NDJSON) report format |
| `action.yml` | Action definition: inputs, defaults and runtime |
| `lib/` | Sources compiled by `tsc` (generated by `npm run build`, not committed) |
| `dist/` | Compiled action (generated by `npm run build`, committed) |
| `test/` | Unit tests of the readers and their fixtures |
| `cucumber/js/` | Cucumber project used to generate the reports for the end-to-end tests of the workflow |

Both readers implement the `ReportReader` interface of `src/types.ts` (`globalInformation`, `failedSteps`, `undefinedSteps`, `pendingSteps`, `listAllScenarioByFile`). `src/main.ts` does not know which format it is reading, so a change in one reader must be done in the other one too.

## Type checking

The action is written in TypeScript, in strict mode (`tsconfig.json`). To check the types of the sources and of the tests:

```bash
npm run typecheck
```

## Running the tests

### Unit tests

```bash
npm test
```

The tests are written in TypeScript and run by mocha with [tsx](https://tsx.is/), which does not check the types: run `npm run typecheck` too.

There is one spec file per module in `test/`:

- `test/reportReader.spec.ts` runs every spec against both readers, with the same expected values: the JSON and NDJSON reports of a fixture describe the same run, so both readers must return the same result.
- `test/main.spec.ts` runs the whole action with fakes of `@actions/core`, `@actions/github`, `@actions/glob` and `fs` (see `test/fakes.ts`), and checks the check requests sent to GitHub, the outputs and the job status.
- The other spec files test the pure functions of `src/`.

### Test fixtures

Each fixture is a feature file in `test/fixtures/features/`. Its steps and hooks are defined in `test/fixtures/support/steps.js`. The reports generated from them are committed in `test/fixtures/reports/`, so the tests do not need to run Cucumber.

To regenerate the reports, after changing a feature file or upgrading `@cucumber/cucumber`:

```bash
node test/fixtures/generate.js
```

The script generates a `<name>.json` and a `<name>.ndjson` report for each feature file. It also generates a `nominal` report from the features in `cucumber/js/`. Local absolute paths are removed from the reports.

To add a fixture:

1. Add a `test/fixtures/features/<name>.feature` file.
2. If it needs new steps or hooks, add them to `test/fixtures/support/steps.js`. Use tagged hooks (`Before({ tags: '@my-tag' }, ...)`) so they only apply to the fixture that needs them.
3. If it needs specific cucumber-js options (e.g. `--retry`), add them to `extraArgs` in `test/fixtures/generate.js`.
4. Run `node test/fixtures/generate.js` and commit the generated reports.

### End-to-end tests

The `Tests` workflow (`.github/workflows/test.yml`) runs the action on reports generated from `cucumber/js/`, in both formats. It checks the conclusion of the job and some outputs. It can only run on GitHub, because the action creates checks through the GitHub API.

To generate the same reports locally:

```bash
npm run cucumber
npm run cucumber-ok
npm run cucumber-undefined
npm run cucumber-non-failed
npm run cucumber-empty
```

These commands exit with an error when scenarios fail: this is expected.

## Building

The action runs `dist/index.js`. The build compiles the sources to `lib/` with `tsc` (`tsconfig.build.json`), then bundles `lib/index.js` with its dependencies with [ncc](https://github.com/vercel/ncc):

```bash
npm run build
```

`dist/` must be rebuilt and committed with every change to the source code or to the dependencies. The `PR check` workflow fails if `dist/index.js` is not up to date.

## Good practices

- **Write a test first when fixing a bug in a reader.** Add a fixture that reproduces the problem, check that the test fails, then fix the code.
- **Keep both readers consistent.** A fix or a feature in one reader must be done and tested in the other one.
- **Test against real reports.** Generate fixtures with cucumber-js instead of writing reports by hand, so the tests follow the format really produced by Cucumber.
- **Document every new input.** A new input must be added to `action.yml` (description and default value) and to the parameters table of `README.md`.
- **Keep the existing style**: TypeScript with ES module syntax (`import`/`export`), 4 spaces indentation.
- **Do not use `any`.** Type the data read from the reports and the injected dependencies (see `src/types.ts`).
- **Use [Conventional Commits](https://www.conventionalcommits.org/)** for commit messages and pull request titles: `feat: ...`, `fix: ...`, `chore: ...`, `docs: ...`, `build: ...`.
- **Rebuild `dist/`** before pushing (see [Building](#building)).
